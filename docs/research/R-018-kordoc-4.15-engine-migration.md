# R-018 — Kordoc 4.2.5 → 4.15.7 엔진 이식과 빌드 하드닝 재작성

- 상태: REQUIRED (M1 사실은 CONFIRMED, M2 이후 항목은 PROPOSED)
- 작성일: 2026-09-28
- 최종 갱신: 2026-09-30
- 기준 버전/커밋: HanMark 2.6.1 a31a191 → 작업 브랜치 `2.7.0`, Kordoc npm 4.15.7 (2026-09-27 배포)
- 관련 문서: R-006, R-009, R-015, R-017, 2.7.0 통합 업데이트 계획
- 담당 범위: 엔진 버전 고정, esbuild 하드닝, 번들·릴리스 검사, 엔진 출력 변화의 영향

## 1. 조사 질문

HanMark의 오프라인·결정적 변환 계약과 Community 심사 조건을 지키면서 Kordoc을 4.2.5에서 4.15.7로 올리려면 무엇을 바꿔야 하고, 사용자에게 보이는 동작은 무엇이 달라지는가?

## 2. 범위

### 포함

- `package.json`·lockfile의 Kordoc 고정, `esbuild.config.mjs`의 Kordoc 소스 변환, `scripts/check-bundle.mjs`·`scripts/check-release.mjs`, 빌드 하드닝 테스트
- 번들 크기, 제3자 코드, 네트워크·프로세스 경로
- Kordoc 변경 이력에서 확인한 Markdown 입출력 변화(영향 목록)

### 제외

- 2.7.0 기능(불러오기 옵션, 공문서 확장, 노트 조립, 비교, 양식, i18n) 구현 자체. 각 기능은 별도 R 문서로 등록한다.
- OCR·수식 OCR·인쇄 PDF·sharp 기반 래스터화(커뮤니티 플러그인에 넣지 않는다).

## 4. 확인된 사실

1. 2.6.1 기준선: `npm run check` 통과, 테스트 265개, `main.js` 3,322,872바이트.
2. Kordoc 4.15.7 라이브러리 그래프는 `index.js`(약 1.2MB)와 청크 12개다. 선택적 OCR·수식 청크(`image-ocr-*`, `formula-*`, `pdf-ocr-*`)도 동적 import로 그래프에 들어온다.
3. 4.2.5 모양에 맞춘 치환 중 **암호 HWPX용 COM 분기 치환이 0회 일치**해 빌드가 멈췄다(`KORDOC_ENCRYPTED_HWPX_COM_BRANCH`). 4.15.7에서 이 분기는 `password` 분기의 `else` 안으로 옮겨졌고 뒤에 배포용 문서 오류가 온다.
4. 나머지 치환은 그대로 맞았다: cfb 로더 2곳(HWP5 파서·HWP5 패처), COM 헬퍼 모듈 1개, 배포용 HWP COM 분기 1곳, PDF 자산 탐색 블록 1곳.
5. 선택적 네이티브 모듈 이름 치환은 `image-ocr` 청크의 안내 문구 속 `'sharp'`까지 바꾸지만, 그 문구가 템플릿 문자열이라 문법이 깨지지 않는다.
6. 이식 후 `main.js`는 3,668,074바이트다(+345,202바이트, +10.4%). 기존 상한 3,459,213바이트를 넘었다.
7. 기존 `check-bundle.mjs`의 `bundle.includes("4.2.5")` 검사는 번들 안의 다른 문자열 때문에 통과하고 있었다. 즉 **엔진 버전을 실제로 검증하지 못했다.** Kordoc은 자기 버전을 `VERSION` 문자열로 넣으므로 `"4.15.7"` 따옴표 포함 검사로 대체했다.
8. Windows 체크아웃(`core.autocrlf=true`)은 `word-assets/*`를 CRLF로 받아 `src/io/embeddedAssets.ts`의 base64가 달라졌다. 같은 커밋이라도 운영체제마다 `main.js`가 달랐다. `.gitattributes`로 해당 파일을 LF로 고정했다.
9. Kordoc SECURITY.md는 4.5 미만을 지원 대상에서 뺀다. 2.6.1의 4.2.5는 보안 수정 대상 밖이었다.
10. 이식 후 기존 테스트 중 실패한 것은 빌드 하드닝 테스트 2개뿐이었다(해시 파일명 `parser-FDOR727T.js`, `new Uint8Array(buffer)` 기대값, COM 파일 2개 가정). 인라인 표·생성·스타일·이미지 테스트는 그대로 통과했다.

## 5. 해석과 제안

- 치환을 앞뒤 문맥 일치에 기대면 Kordoc 내부 정리만으로도 깨진다. COM 분기는 가드 조건(`isComFallbackAvailable() && options?.filePath`)을 찾아 중괄호 짝을 맞춰 문장 전체를 지우는 방식으로 바꿨다(문자열·템플릿·주석 속 중괄호 무시).
- 개수 검사는 파일별이 아니라 **빌드 전체 합계**를 `KORDOC_HARDENING_MANIFEST`(버전·cfb 2·COM 헬퍼 1·COM 분기 2·PDF 탐색 1)와 대조한다. 설치된 Kordoc 버전이 매니페스트와 다르면 빌드가 시작되지 않는다.
- 번들 상한은 3,780,000바이트(실측 +약 3%)로 다시 잡았다. 2.7.0 기능(한국어 CMap 약 214KB base64, 표준 기안문 서식, 영어 문구, 각주 플러그인)을 넣을 때마다 실측과 사유를 이 문서 변경 이력에 남기고 올린다. (PROPOSED)
- 다음 단계(M2, PROPOSED): PDF 자산 탐색 블록은 지우는 대신 내장 한국어 CMap 공급자를 주입한다. 생성 각주 autoNum 보완, 기본 모드 긴 표 머리행 반복, HWPX 최종 ZIP 날짜 고정, 예전 노트 패치 차단을 적용한다.

## 6. 대안과 기각 사유

| 대안 | 장점 | 위험/기각 사유 | 재검토 조건 |
|---|---|---|---|
| 4.2.5 유지 | 변경 없음 | 보안 지원 밖, 표·PDF·각주 개선 포기 | 없음 |
| Kordoc을 소스에서 직접 빌드해 번들 | 모듈 경계를 알고 치환 가능 | 빌드 체인·버전 추적 부담, 배포 원본과 달라짐 | 상위가 라이브러리 전용 경량 진입점을 낼 때 |
| `child_process` 모듈만 스텁 | 간단 | 호출 코드가 남아 Community 스캐너·검토 부담 | 없음 |
| 번들 상한 제거 | 편함 | 의도하지 않은 비대화를 못 잡음 | 없음 |

## 7. 한계와 미해결 질문

- Kordoc 불러오기 Markdown 표기가 여러 곳 바뀌었다(4.14.3 이스케이프 `\$`·`\|`, 각주 참조 "(주: …)", 4.15.7 체크박스 ☐/☑, 밑줄 `<u>` 등). 자동 테스트는 통과했지만, 실제 문서 회귀 코퍼스로 확인하는 일은 M2에 남아 있다.
- 공문서 v5 엔진의 모양 변화와 자동 다듬기(법령 코드 삭제 등)는 한컴 실표시로 확인해야 한다.
- 생성 각주의 autoNum은 Kordoc main에만 있고 npm 배포본에는 없다(상위 커밋 b8c0c52).
